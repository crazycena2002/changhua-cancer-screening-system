# 流程校正成果與後續介接

更新日期：2026-10-05。第一階段原始差異與分類見 [流程校正盤點.md](流程校正盤點.md)。本次沿用既有 route、Vue view、共用元件、CSS、Pinia store 與手機／桌機版型。

## 已調整

1. `/booking` 入口改為「我有邀約碼／一般篩檢預約」。一般流程先以身分證與出生年月日比對模擬名冊，再列出符合資格的子抹、乳攝、糞便潛血項目，並保留年齡及篩檢紀錄的 DEMO 資格條件。糞便潛血直接進入院所領管，沒有檢查時段選項。
2. 邀約碼及設站沿用既有場次、額滿時段不可點、手機 OTP、基本資料與可修改現居地址。基本資料之後再次判斷其他項目資格，讓民眾自行加選，接著選填／驗證 E-mail 並完成預約。保留多項目同批名額核對與原子建立，列為「優化流程」。
3. 腸篩名單的六個生命週期狀態依列印、確認接收、確認領管、繳管、確認送驗操作推進。已接收／已領取後 7／14 天自動計算未領取、退管、未繳回、報廢提醒，提醒不覆寫管件生命週期；可在名單查詢與 CSV 中檢視。補印不變更狀態；取消列印只接受尚未接收的已派送紀錄。
4. 腸篩公休日曆可繼續切換未來月份。原有週一至週日、多時段、QR／條碼比對、批次繳管及 10 分鐘內復原均保留。
5. 新增本機示範用「所屬機構＋角色＋功能權限」模型，包含系統管理員、衛生局承辦、衛生所承辦、醫療院所人員、藥局人員、單位管理者、一般使用者。後台選單、查詢資料、部分寫入及匯出依權限判斷；帳號申請仍只允許自行申請一般使用者或單位管理者，並保留同機構管理者唯一檢查。

## 仍需後端 API 與正式資料

- 邀約名冊、身分資料、出生日期及篩檢資格查詢；不可把前端 DEMO 年齡門檻當作正式政策。
- SMS／E-mail OTP 發送與伺服器驗證；現有 DEMO 驗證碼顯示在畫面上。
- 預約、活動、合作院所、領管服務時間、名額、糞管狀態的資料庫模型與交易；公開名額扣減需要並發保護。
- 伺服器端 RBAC、機構隸屬與查詢範圍、操作稽核、禁止第二位單位管理者的資料庫唯一約束。前端 `accessPolicy.js` 只用於本機示範，重新整理會重設 session；直接開啟後台仍以展示管理員進入，不能作為正式安全防護。
- 7／14 天追蹤排程與通知、退管／報廢業務確認、正式時區與假日規則。目前提醒由開啟名單的前端依日期計算，不會在無人開啟頁面時執行批次工作。
- Excel `.xlsx` 匯出、標籤機與 QR 掃描設備整合；目前匯出為 Excel 可開啟的 CSV，標籤為瀏覽器列印。

## 建議下一步

1. 先定義整篩、設站、腸篩三種獨立業務資料模型與 API 合約，保留共用活動入口。
2. 建立後端預約交易、OTP、資格及 RBAC，逐一替換本機模擬資料。
3. 建立糞管生命週期事件紀錄、排程提醒與稽核紀錄，再接標籤機及真正的 Excel 匯出。
4. 在正式 API 可用後，進行桌機與手機的端對端驗收，含不同角色、額滿、重複預約、逾期提醒與跨裝置同步。
